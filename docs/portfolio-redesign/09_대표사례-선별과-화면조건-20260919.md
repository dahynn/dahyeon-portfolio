# 공개 포트폴리오 대표 사례 제안

작성: 2026-09-19 · 상태: 제안 완료 / 공개 문구·개인 역할 확정 및 UI 반영 전

## 결론

기존 소개 순서인 **CapSure → Roundy → SAN**을 유지하고 각 프로젝트에 대표 사례 2개만 둡니다. CapSure는 거래·계약 상태, Roundy는 동시 요청·인증 일회성, SAN은 조회 비용·생성 근거 보존을 맡습니다. 다시봄은 이번 3개 패킷 비교 대상이 아니므로 기존 짧은 소개를 유지하는 제안입니다.

| 순서 | 공개 제목 후보 | 선택 이유 |
| --- | --- | --- |
| CapSure 01 | 승인 뒤 증권 발행이 실패해도, 같은 결제를 다시 승인하지 않도록 | 외부 승인과 내부 계약의 불일치, 복구 후 단일 결과를 구체적으로 설명할 수 있음 |
| CapSure 02 | 배치가 늦어도, 입금 시점에 계약 효력이 달라지지 않도록 | 합성 보험 업무 규칙을 시간 경계로 검증한 사례로 01과 구별됨 |
| Roundy 01 | 늦게 도착한 요청이 새 방 배정을 지우지 않도록 | 원자적 입장만으로 해결되지 않은 중간 결과와 추가 판단이 있음 |
| Roundy 02 | 인증 결과는 본인만, 한 번만 사용하도록 | 16개 소비 요청 중 1개 성공이라는 좁고 명확한 검증과 얼굴 인증 화면이 연결됨 |
| SAN 01 | 서버 검색으로 옮긴 뒤에도 남은 태그 집계 비용을 줄이기 | 화면·서버·쿼리와 결과 집합 비교까지 연결된 성능 문제 해결 |
| SAN 02 | 원문이 바뀌어도, AI가 읽은 입력은 확인할 수 있도록 | 생성 품질을 과장하지 않고 비동기 입력의 재현성을 설명할 수 있음 |

기존 영상의 전체 음성 피드백을 확인했다는 뜻은 아닙니다. 기존 기록에서 확인된 템플릿의 문제·판단/원인·해결 과정·비교/검증 틀을 사용합니다.

## 1. CapSure — 승인 이후 내부 처리 실패의 복구

**문제.** 합성 PG 승인이 끝난 직후 증권 저장소에 예외를 주입했습니다. 사용자에게는 HTTP 500이 반환됐지만, 외부 승인은 내부 트랜잭션과 함께 취소되지 않습니다. 오류 응답만 보고 새 승인을 보내면 이미 승인된 주문을 중복 처리할 위험이 있었습니다.

**판단.** ‘실패 응답’과 ‘결제 실패’를 구분했습니다. 승인 후 내부 처리 실패는 `APPROVING`, 승인 여부를 모르는 timeout은 `UNKNOWN`으로 남깁니다. 두 상태를 같은 실험 결과처럼 합치지 않고, 기존 주문의 외부 결과를 확인한 다음 내부 처리를 이어가는 기준입니다.

**구현.** `PaymentService`의 멱등 처리와 조회·대사 경로를 사용해 같은 주문을 복구합니다. 계약 활성화, 증권, Outbox가 각각 한 건으로 수렴하는지 확인합니다. 배치에는 처리 결과와 체크포인트를 남겨 중단 지점 뒤에서 재개할 수 있도록 했습니다.

**검증 결과.** 기존 `PaymentPolicyIntegrationTest` 기록에서 예외 직후 `APPROVING / PENDING_INITIAL_PREMIUM / 증권 0건`, 같은 주문 대사 후 `PAID / ACTIVE / 증권 1건`을 확인했습니다. 동일 confirm 100회 시험은 별도 검증으로, 외부 승인 호출·시도·증권·활성화 이벤트가 각각 1회/1건 유지됐습니다. 2026-09-13 해당 XML은 10건 통과입니다. 이번 제안 작업에서는 재실행하지 않았습니다.

**화면 조건.** 같은 합성 주문의 ‘결과 확인 중’과 복구 후 계약/증권 화면을 같은 크기로 두 장 사용합니다. UI가 `APPROVING`을 직접 보여주지 않으면 화면에 해당 상태를 합성하지 않습니다. 실제 API/테스트 응답을 별도 검증 영역에 두고, 주문 별칭·상태·건수만 읽히게 발췌합니다. 캡처에는 합성 PG 시험임을 표시하고 Toss sandbox 사진을 이 장애 재현의 증거처럼 붙이지 않습니다.

**금융 업무 적용 관점 — INFERENCE.** 수납 응답이 끊겼을 때 재승인보다 거래 확인을 우선하고, 계약 활성화까지 복구 완료 조건에 포함하는 설계 관점입니다. 한화생명의 실제 결제 구조·정책을 구현했다는 의미가 아닙니다.

**내부 근거.** CapSure 최신 패킷 §1, `CLM-PAY-001~004`, 커밋 `f7485ad / 6721f4f / 2d744a7`. 1만 건 시험은 보조 근거로만 보관합니다. 이는 합성 UNKNOWN을 FAILED로 확정한 대사이며 성공 결제 건수가 아닙니다.

## 2. CapSure — 배치와 지연 입금의 시간 경계

**문제.** 시험 시계를 유예 종료 다음 날로 옮기고 일일 실효 배치보다 수납을 먼저 실행했습니다. DB에 남아 있는 `GRACE`만 보고 완납 시 `ACTIVE`로 바꾸면 배치 실행 순서 때문에 계약 효력이 달라질 수 있었습니다.

**판단.** ‘돈이 들어왔다’와 ‘보장이 유효하다’를 분리했습니다. 수납 순간에도 업무일 기준의 효력 규칙을 적용하고, 실효 후 입금은 기록하되 자동으로 활성화하지 않는 기준입니다. 실제 보험의 보편 규칙이 아니라 합성 상품의 시험 정책입니다.

**구현.** `PremiumCollectionService`가 수납 전 `PremiumDelinquencyService.beforeSettlement`를 호출합니다. 계약을 잠근 뒤 배치와 같은 만료 규칙을 적용하고, 수납 후에는 모든 미납 회차의 해소 여부를 확인합니다. 실효 후 수납은 `pay_late_settlement_review`에 남깁니다.

**검증 결과.** 합성 정책에서 유예 마지막 날 완납은 ACTIVE, 다음 날 배치 전 입금은 LAPSED 및 지연 검토 1건입니다. 이미 실효된 계약의 UNKNOWN 출금 결과를 같은 키로 두 번 반영해도 수납·검토가 각각 1건으로 유지됐습니다. 기존 2026-09-13 미납 통합 테스트 XML 18건 통과 기록을 사용합니다. 45건 배치 재개 시험은 본문을 복잡하게 만들지 않도록 면접용 보조 근거로 둡니다.

**화면 조건.** 합성 계약의 마지막 날/다음 날 상태를 나란히 비교합니다. 캡처 당시 업무일과 동일 시험 정책을 표시하고 계약 상태·수납 내역·검토 상태를 보여줍니다. 미납·검토 UI가 없으면 기존 증권/청구 화면은 서비스 설명용으로만 쓰고, 시간선과 실제 테스트 출력으로 경계를 증명합니다. 정상 가입 화면만으로 실효 처리까지 증명하지 않습니다.

**금융 업무 적용 관점 — INFERENCE.** 배치 지연이나 늦은 입금에도 동일한 효력 판단을 적용하는 관점입니다. 실무 적용 시 상품 약관·통지·부활 조건은 별도로 확정해야 합니다.

**내부 근거.** CapSure 패킷 §2, `CLM-STATE-001~003`, `d1b12f3 / 6721f4f`.

## 3. Roundy — 원자적 입장과 오래된 정리 요청

**문제.** 제어된 로컬 실험에서 매칭 완료 후 늦은 poll이 사용자를 다시 대기열에 넣었습니다. 이전 방의 종료 처리가 새 배정 뒤 도착하면 새 `currentRoom`도 삭제됐습니다. 정상적인 6명 입장 화면만으로는 드러나지 않는 순서 문제였습니다.

**판단.** 인증 소비·큐 등록·방 배정은 하나의 전이로 묶되, 종료 요청에는 ‘지우려는 방이 지금 방인가’라는 조건이 따로 필요했습니다. 원자적 입장만 반영한 중간 버전에서도 새 배정 유실은 100/100회 발생했으므로 원자화만으로 완료로 보지 않았습니다.

**구현.** Redis Lua에서 최초 인증 소비와 큐 조작, 남녀 각 3명 선택 및 배정을 함께 처리합니다. `cleanup-room.lua`는 현재 매핑이 정리 대상 roomId와 같은 경우에만 삭제합니다. 이 원자성의 범위는 단일 Redis 실행입니다.

**검증 결과.** 실제 격리 Redis 8.4.0과 모의 JWT/DB를 사용하는 로컬 Controller 시험에서 지연 poll 재큐잉과 늦은 정리의 새 배정 유실이 각각 100/100 → 0/100으로 기록됐습니다. 동일 사용자 최초 요청의 업무 거절 977/1,600 → 0/1,600은 별도 조건입니다. HTTP·실제 DB·영상 연결은 이 실험 대상이 아닙니다.

**화면 조건.** 매칭 대기→방 배정 실제 화면은 맥락용으로 한 장 크게 사용합니다. 그 옆에는 ‘새 방 B 배정 → 옛 방 A 정리 도착 → B 유지’ 세 단계 설명 도식과 기존 시험 결과 발췌를 둡니다. 서비스 UI처럼 만든 가짜 Redis 대시보드는 사용하지 않습니다. 새 캡처가 필요하면 테스트 계정으로 같은 사용자/방의 대응을 확인하고 사람 얼굴·실명·토큰은 제외합니다.

**금융 업무 적용 관점 — INFERENCE.** 늦은 취소나 재요청이 최신 신청 상태를 덮어쓰지 않도록 전이 조건과 소유권을 함께 검사하는 관점입니다. 금융 원장의 정합성까지 증명한 사례는 아닙니다.

**내부 근거.** Roundy 패킷 §1, `CLM-RND-001~002`, `6e60b8d → 988e2f6 → b960772 → 36cc993`. AWS 합성 9,000명 HTTP 매칭 기록은 별도 상세보기 후보이며 제목 수치로 쓰지 않습니다. 영상 동접이나 실서비스 무실패로 표현하지 않습니다.

## 4. Roundy — 사용자 귀속 인증 결과의 일회 소비

**문제.** 인증 성공 여부만 검사하면 타인 요청이나 겹친 소비 요청이 같은 결과를 사용할 위험이 있습니다. PENDING을 먼저 지우거나, 소비 후 늦은 완료 응답이 인증을 되살리는 조건도 검사할 필요가 있었습니다. 실제 탈취 사고가 발생한 것으로 서술하지 않습니다.

**판단.** 소유자·요청·상태·소비 횟수를 함께 제한합니다. PENDING은 유지하고 VERIFIED만 소비하며, 이미 끝난 요청은 늦게 도착한 성공으로 되살리지 않는 기준입니다.

**구현.** `verify:{userId}:{requestId}`에 귀속시키고 완료 Lua는 PENDING만 VERIFIED/FAILED로 바꿉니다. 소비 Lua는 VERIFIED일 때만 삭제합니다. 최초 입장에서는 소비와 큐 등록을 같은 Lua 실행으로 연결합니다.

**검증 결과.** 기존 `VerificationRedisTest` 6건 통과 기록에서 타인 소비 실패, 소유자 최초 소비 성공, 재소비 실패와 늦은 완료 결과의 재생성 차단을 확인했습니다. 8개 워커에 제출한 16개 소비 요청 중 1개만 성공했습니다. 실제 Redis·모의 DB 조건이며 얼굴 AI 정확도나 금융 실명인증 성능 검증이 아닙니다.

**화면 조건.** 사용자 요청대로 얼굴 인증 PNG 하나만 크게 보여줍니다. 투표 화면을 인증 사례에 섞지 않습니다. 인증 상태 PENDING→VERIFIED→소비를 작은 설명 도식으로 보조하고, 동시 소비 결과는 테스트 출력에 따로 표시합니다. 원본 얼굴의 공개 동의·비식별 처리가 불확실하면 재촬영하지 않고 적법한 테스트 이미지/승인된 비식별 캡처만 사용합니다.

**금융 업무 적용 관점 — INFERENCE.** 본인확인 이후 민감 작업의 승인 결과를 사용자·요청에 묶고, 중복·지연 요청에서도 일회성을 확인하는 접근입니다.

**내부 근거.** Roundy 패킷 §2, `CLM-RND-003`, `32ec1ff / 988e2f6`, `backend-tests-summary.json`. TTL 존재 확인과 실제 만료 대기 시험을 혼동하지 않습니다.

## 5. SAN — 서버 검색 이후 남은 쿼리 비용과 결과 완결성

**문제.** 전체 카드 다운로드 후 브라우저 필터링은 데이터가 늘수록 전송과 처리 비용이 커집니다. 중앙 인계는 서버 검색으로 전환한 중간 단계에도 태그 집계 병목이 남았다고 보고합니다. 저장된 중간 측정 파일·쿼리 계획은 존재하지만, 이번 선별 작업에서 중간 단계 원시 실행계획 전체를 재분석하지는 않았습니다.

**판단.** 반환 개수만 줄이는 것으로 끝내지 않고 태그 조건을 처리하는 쿼리와 실제 응답 비용을 함께 확인합니다. 성능 향상과 별도로 결과 집합 일치·사용자 격리·복수 태그 AND·기간 경계·안정 정렬을 검증 기준으로 둡니다.

**구현.** `b2711eb`의 검색 쿼리는 태그별 카드 ID를 `GROUP BY/HAVING COUNT(DISTINCT ...)`로 모아 필터링하며, `createdAt DESC, cardId DESC`로 안정 정렬합니다. `c629e77`에서 프런트를 서버 파라미터 요청으로 연결하고 `1c8c252`에 비교·회귀 하네스와 중간/최종 기록을 보존했습니다. 무인자 기존 전체 목록 호출의 호환성도 구분합니다.

**검증 결과.** 기존 로컬 합성 1만 건·워밍업 3회·20회 반복 기록에서 최신 50개 조회 p95 128.15→28.50ms, 조건 검색 첫 50개 p95 133.67→19.04ms입니다. 최신 조회 응답은 5,085,664→26,903B입니다. HTTP 수신·JSON 파싱·기준선 클라이언트 필터가 포함된 과업 비교이며 순수 SQL 시간이나 현재 운영 성과가 아닙니다. 100건 최신 조회는 18.97→23.67ms로 악화했습니다.

**공개 조건.** 본문 검증 영역에 ‘로컬 합성 1만 건·20회·개발 브랜치 검증’을 짧게 명시합니다. 성능 커밋은 수신 기준 main 조상이 아니므로 현재 서비스 적용 완료로 쓰지 않습니다. 중간 병목 원인을 상세히 말하려면 `explain-optimized-before-tag-query-rewrite-10000.jsonl`과 최종 계획을 추가 대조합니다. 그전에는 제목을 ‘전체 다운로드 대신, 필요한 결과만 정확하게 조회하도록’으로 좁혀도 됩니다.

## 6. SAN — 비동기 AI 생성 입력의 시점 고정

**문제.** 생성 요청 이후 원문이 바뀌면 비동기 작업이 읽는 내용과 사용자가 나중에 보는 근거가 달라질 수 있습니다. 이 사례는 실제 운영 오답 사고가 아니라 입력 계약의 시간차 위험과 이를 제한한 구현 사례로 설명합니다.

**판단.** 최신 원문을 다시 읽는 편의보다 ‘이번 생성에 무엇을 전달했는가’를 재현하는 기준을 택합니다. 원문과 외부 AI에 전달한 입력을 구분해 남기며, 고정된 입력만으로 비동기 요청을 재구성합니다.

**구현.** `TilSourceService.captureSnapshots`가 카드·스크랩 ID, 제목, 원문, URL과 AI 입력 내용을 스냅샷으로 만듭니다. `toAiContents`는 현재 카드를 다시 조회하지 않고 `DailySummary`의 스냅샷에서 요청을 구성합니다. 화면의 생성 근거도 고정된 스냅샷과 연결합니다.

**검증 결과.** 이번 읽기에서 `TilSourceServiceTest`의 카드 ID·원문·정제 입력 보존 assertion과 `toAiContents`가 저장한 정제 입력을 반환하는 assertion을 확인했습니다. 기존 합성/mock 검증 기록과 현재 코드는 구분합니다. ‘원문 변경 후 전체 UI/API E2E 성공’은 이번에 새로 입증하지 않았습니다. 최근 선택 클래스 재실행은 Gradle offline 플러그인 캐시 부재로 시작 전 실패한 상태입니다. `SRC-xx`는 입력 식별자이지 문장별 사실 검증이 아닙니다.

**화면 조건.** 실제 TIL의 생성 결과와 SOURCE 패널을 보여주되 합성 텍스트로 구성합니다. 생성 요청 → 원문 변경 → 기존 TIL의 저장 입력 유지 장면은 별도 재현이 필요합니다. UI에 원문·AI 전달문을 함께 표시하는 기능이 없으면 API/테스트 증거를 별도로 붙이고 가짜 패널을 만들지 않습니다. 현재 사용자 제공 TIL 사진은 서비스 소개용이며 입력 고정의 동작 증거로 승격하지 않습니다.

**금융 업무 적용 관점 — INFERENCE.** 업무 보조 AI의 결과를 검토할 때 생성 당시 입력을 추적할 수 있게 설계하는 관점입니다. 실제 감사 기준 충족·개인정보 보호 완결성·환각 제거를 주장하지 않습니다.
